# Практическая №1: локальный Lakehouse, вариант 1 (TPC-H Q3)

Автор: **Якупова Нелли Рафаэлевна**. GitHub: https://github.com/NelliYak.

Данные: TPC-H `sf1`. Бизнес-задача: топ-10 заказов клиентов BUILDING, оформленных до 1995-03-15, по выручке позиций, отгруженных после этой даты.

## Запуск на Windows

Требуются Docker Desktop (Linux containers), Docker Compose и Python 3.11+.
Откройте PowerShell в папке проекта:

Полный запуск, включая Spark и отчёт: `powershell -ExecutionPolicy Bypass -File .\start.ps1`.

```powershell
docker compose up -d minio lakekeeper trino
python scripts/setup.py
python scripts/run.py
```

`setup.py` ждёт Lakekeeper, создаёт бакет и каталог practice. `run.py` создаёт таблицы, проверяет данные, строит Silver/Gold, проводит бенчмарк и демонстрирует изменение схемы и восстановление снапшота. Скрипт повторного выполнения пересоздаёт **только учебные таблицы этого проекта**. SQL-файлы сохраняются в `sql/`, результаты — в `results/`.

Первый запуск скачивает контейнеры; при сетевой ошибке повторите `docker compose up`. Данные сохраняются в именованных Docker volumes. Обычная остановка сохраняет данные:

```powershell
docker compose stop
docker compose start
```

## Сервисы

| Сервис | Назначение | Адрес |
|---|---|---|
| Silo (форк MinIO), имя сервиса `minio` | S3-хранилище файлов Iceberg | http://localhost:9001 |
| PostgreSQL 16 | Метаданные Lakekeeper | Только сеть Docker |
| Lakekeeper 0.14.0 | Iceberg REST Catalog | http://localhost:8181 |
| Trino 476 | SQL, генератор TPC-H, ELT, измерения | http://localhost:8080 |
| Spark 3.5.3 | Дополнительный движок: читает Bronze через JDBC Trino | Запускается отдельно |

В консоли Silo: пользователь `student`, пароль `student-local-password`, бакет `lakehouse`.
Это локальные учебные реквизиты: HTTP-порты привязаны к 127.0.0.1. Настройки не предназначены для публичного сервера.

Silo выбран вместо исходного MinIO: старый официальный Docker-образ и архив бинарника при настройке оказались недоступны. Silo используется в актуальном официальном минимальном примере Lakekeeper. Он сохраняет S3-интерфейс и роль объектного хранилища. Эта замена указана явно, а не представлена как исходный MinIO.

## Архитектура и слои

`TPC-H → Trino → Iceberg Bronze → Iceberg Silver → Iceberg Gold`.
Trino обращается к Lakekeeper за каталогом, к Silo — за файлами. PostgreSQL хранит служебные данные каталога, а не строки заказов. Iceberg — табличный формат; Parquet и ORC — форматы файлов внутри таблиц.

Bronze: исходные значения customer, orders, lineitem; только необходимые колонки плюс linenumber для ключа позиции. Silver: проверки качества, нормализация сегмента, фильтры Q3, соединение и выручка позиции. Денежные значения преобразуются в DECIMAL, чтобы суммирование не накапливало погрешность двоичной арифметики. Gold: выручка по заказу и топ-10.

Партиционирование не используется: sf1 и выбранные колонки сравнительно невелики, а отдельные партиции увеличили бы число маленьких файлов. Во всех комбинациях условия одинаковы.

## Методология бенчмарка

В Trino 476 кодек задаётся как `SET SESSION iceberg.compression_codec='GZIP'` (в Python-клиенте — заголовок X-Trino-Session). Свойство таблицы compression_codec из более новой документации для этой версии не используется. У ORC настройка Trino GZIP соответствует внутреннему кодеку **ZLIB**, у Parquet — GZIP. Соответствие проверено в исходном коде Trino 476 HiveCompressionCodec.

Сравниваются PARQUET/GZIP, PARQUET/ZSTD, ORC/GZIP, ORC/ZSTD. Все таблицы содержат одинаковые значения и колонки, генерируемые tpch.sf1. Для каждой комбинации записаны три таблицы; замер записи — сумма времени CTAS всех трёх. Запись измеряется один раз на комбинацию и поэтому является ориентировочной, с влиянием прогрева.

Время запроса — полное клиентское wall-clock время от отправки SQL до получения результата. Оно включает планирование, выполнение, сеть и опрос REST API (пауза 50 мс). В query_log.json и benchmark.json сохранены query id, серверная статистика и отдельные прогоны. Перед измерениями выполняется один прогрев каждой комбинации, затем пять измерений с чередованием порядка. Показаны медиана, минимум и максимум. Это **прогретый локальный тест**, кеш ОС между запусками не очищается.

Q3 выполняется непосредственно по каждой копии Bronze: чтение Gold не могло бы измерить влияние кодека Bronze. Результаты всех запросов сверяются с исходным tpch.sf1. Gold проверяется отдельно с допуском 0.00001 по выручке, поскольку исходный запрос использует DOUBLE, а витрина — DECIMAL.

Размер — сумма `file_size_in_bytes` из `$files` для текущих активных файлов трёх таблиц. МБ = байты / 1 000 000. Метаданные Iceberg, исторические снапшоты и файлы удалений не включены. Это размер текущих файлов данных, а не размер всего Docker volume. SHOW STATS не используется как измеритель физического размера.

Измерения зависят от компьютера, числа файлов, фоновой нагрузки и кешей. Они не являются официальными результатами TPC-H и не доказывают универсальное превосходство кодека. Таблицы Bronze создаются без искусственной очистки: нарушения, если обнаружены, должны быть исправлены осознанно; скрипт останавливается при ненулевых счётчиках качества.

## Дополнительный инструмент: Spark

JDBC-драйвер не хранится в git. Скачайте фиксированную версию:

```powershell
Invoke-WebRequest 'https://repo.maven.apache.org/maven2/io/trino/trino-jdbc/476/trino-jdbc-476.jar' -OutFile 'scripts/trino-jdbc-476.jar'
docker compose --profile tools run --rm spark
```

Spark читает `iceberg.bronze.customer` через Trino JDBC, выводит схему и пять строк, затем группирует клиентов по сегменту. Сумма клиентов проверяется: 150000. Результат сохраняется в `results/spark_bronze.json`. Агрегация DataFrame выполняется Spark; Trino предоставляет доступ к таблице. Прямой доступ Spark к Iceberg REST Catalog в этой работе не настраивается. Преимущество для учебной задачи — повторное использование проверенного SQL-шлюза без дополнительной конфигурации S3; Doris/StarRocks потребовали бы отдельной настройки аналитического сервиса.

## Проверки и восстановление

`results/checks.json`: пропуски, диапазоны скидок/цен, дубли ключей, потерянные связи, совпадение Gold и эталона, изменение схемы, восстановление снапшота.
Для schema evolution добавляется source_system, затем переименовывается в data_source. У существующих строк поле NULL.
Для time travel сохраняется snapshot_id Silver, удаляются позиции одного заказа, читается прежняя версия, затем выполняется rollback_to_snapshot. Число строк после восстановления должно совпасть с исходным. Snapshot id в `sql/time_travel.sql` относится к конкретному запуску: для нового эксперимента сначала выберите актуальный id из `$snapshots`.
