# Практическая работа № 1 — Локальный Lakehouse

**Дисциплина:** Основы теории информации  
**Вариант:** 1 — TPC-H Q3 (Shipping Priority)  
**Масштаб данных:** `sf1`

## О проекте

Проект посвящён развёртыванию локального Lakehouse, реализации ELT-процесса и исследованию влияния форматов хранения и алгоритмов сжатия на производительность аналитических запросов.

В качестве источника данных используется TPC-H — набор данных для тестирования аналитических систем.

**Цель работы** — построить конвейер обработки данных от исходных таблиц до аналитической витрины, проверить корректность преобразований и сравнить производительность различных конфигураций хранения.

### Основные задачи

- Развернуть локальную инфраструктуру Lakehouse с помощью Docker Compose.
- Загрузить исходные данные TPC-H в слой Bronze.
- Выполнить очистку, проверки качества и преобразования данных.
- Построить слои Silver и Gold.
- Сравнить Parquet и ORC с кодеками GZIP и ZSTD.
- Измерить размер файлов, время записи и выполнения аналитических запросов.
- Проверить изменение схемы таблицы и восстановление данных из снимка.
- Подключить Apache Spark и выполнить обработку данных Bronze.

## 1. Используемые технологии

| Технология | Назначение |
|---|---|
| Docker Compose | Развёртывание и управление сервисами |
| Silo | S3-совместимое объектное хранилище |
| PostgreSQL 16 | Хранение метаданных Lakekeeper |
| Lakekeeper 0.14.0 | Каталог таблиц Apache Iceberg |
| Trino 476 | SQL-движок для запросов и ELT |
| Apache Iceberg | Табличный формат с поддержкой снимков и изменения схемы |
| Apache Spark 3.5.3 | Дополнительная обработка данных через JDBC |
| Python 3.11+ | Автоматизация запуска, проверок и бенчмарка |
| Parquet, ORC | Форматы хранения файлов |
| GZIP, ZSTD | Алгоритмы сжатия данных |

**Почему используется Silo?**

Вместо MinIO используется Silo — S3-совместимое объектное хранилище, выбранное для совместимости с используемой конфигурацией Lakekeeper. Оно выполняет ту же основную роль в архитектуре проекта: хранит файлы таблиц Iceberg.

## 2. Архитектура Lakehouse

В проекте используется трёхслойная архитектура обработки данных — Bronze, Silver и Gold.

```text
                 TPC-H (sf1)
                      |
                      v
                Apache Trino
                      |
                      v
              Bronze — исходные данные
                      |
                      v
              Silver — обработанные данные
                      |
                      v
               Gold — аналитическая витрина
                      |
                      v
              Результаты запроса Q3

   Lakekeeper — каталог таблиц Iceberg
   PostgreSQL — метаданные каталога
   Silo — объектное хранение файлов
```

Trino выполняет SQL-запросы и преобразования, Lakekeeper предоставляет каталог метаданных, PostgreSQL хранит служебную информацию каталога, а Silo сохраняет файлы данных.

### Слои данных

| Слой | Содержание | Назначение |
|---|---|---|
| Bronze | Исходные данные `customer`, `orders`, `lineitem` | Сохранение данных источника |
| Silver | Проверенные и преобразованные данные, соединённые таблицы | Подготовка данных для аналитики |
| Gold | Выручка по заказам и топ-10 результатов | Представление итоговых бизнес-показателей |

В Bronze сохраняются необходимые для запроса колонки. В Silver выполняются проверки качества, нормализация сегмента клиентов, фильтрация по датам и соединение таблиц. Денежные значения преобразуются в `DECIMAL`, чтобы избежать накопления погрешности при суммировании чисел с плавающей точкой.

В Gold формируется итоговая витрина с идентификатором заказа, выручкой, датой заказа и приоритетом отгрузки.

Партиционирование не используется: для масштаба `sf1` оно не требуется и могло бы увеличить количество небольших файлов.

## 3. Аналитическая задача — TPC-H Q3

Вариант 1 соответствует запросу **Q3 — Shipping Priority**.

Задача заключается в определении десяти заказов с наибольшей выручкой при соблюдении следующих условий:

- Клиент относится к сегменту `BUILDING`.
- Дата заказа раньше 15 марта 1995 года.
- Дата отгрузки позже 15 марта 1995 года.
- Выручка рассчитывается с учётом скидки.

Формула выручки:

```sql
SUM(extendedprice * (1 - discount))
```

Для получения результата объединяются таблицы `customer`, `orders` и `lineitem`. Затем данные фильтруются по сегменту клиента и датам, агрегируются по заказу и сортируются по убыванию выручки.

Результат содержит десять заказов с наибольшей рассчитанной выручкой.

## 4. Запуск проекта

### Требования

Перед запуском необходимо установить:

- Docker Desktop с поддержкой Linux-контейнеров;
- Docker Compose;
- Python 3.11 или новее.

Все команды ниже выполняются в PowerShell из корневой папки проекта.

### Полный запуск

```powershell
powershell -ExecutionPolicy Bypass -File .\start.ps1
```

Скрипт запускает инфраструктуру, выполняет подготовку каталога, ELT-преобразования, проверки, бенчмарк и дополнительный сценарий Spark.

### Пошаговый запуск

Если требуется выполнить основные этапы отдельно:

**1. Запустить инфраструктуру**

```powershell
docker compose up -d minio lakekeeper trino
```

**2. Подготовить каталог и хранилище**

```powershell
python scripts/setup.py
```

Скрипт ожидает готовности Lakekeeper, создаёт бакет и подготавливает каталог `practice`.

**3. Выполнить ELT и бенчмарк**

```powershell
python scripts/run.py
```

Скрипт создаёт таблицы, проверяет качество данных, строит Silver и Gold, выполняет измерения и демонстрирует работу со схемой и снимками таблиц.

Повторный запуск пересоздаёт учебные таблицы проекта.

### Доступ к сервисам

| Сервис | Адрес или способ доступа |
|---|---|
| Silo Console | http://localhost:9001 |
| Lakekeeper | http://localhost:8181 |
| Trino | http://localhost:8080 |
| PostgreSQL | Внутренняя сеть Docker |
| Spark | Запускается отдельной командой |

Для локальной консоли Silo используются учебные реквизиты, указанные в конфигурации проекта. Настройки предназначены только для локального окружения и не рассчитаны на публичный сервер.

### Остановка и повторный запуск

Остановить сервисы без удаления данных:

```powershell
docker compose stop
```

Повторно запустить:

```powershell
docker compose start
```

Данные сохраняются в именованных Docker volumes.

## 5. Методология бенчмарка

Для сравнения используются четыре комбинации формата файла и алгоритма сжатия:

| Формат | Кодек |
|---|---|
| Parquet | GZIP |
| Parquet | ZSTD |
| ORC | GZIP |
| ORC | ZSTD |

Для каждой конфигурации создаются три таблицы Bronze с одинаковыми данными и колонками.

### Что измеряется

**Размер данных.** Рассчитывается по сумме `file_size_in_bytes` активных файлов данных трёх таблиц Bronze. Размер переводится в мегабайты делением на 1 000 000. Метаданные Iceberg и исторические снимки не включаются.

**Время записи.** Суммируется время создания трёх таблиц. Для каждой комбинации выполняется один замер, поэтому результаты записи являются ориентировочными.

**Время выполнения запроса.** Измеряется полное клиентское время выполнения SQL-запроса. Перед измерениями выполняется прогрев, после которого проводятся пять запусков с чередованием порядка конфигураций. Для сравнения используются медиана, минимум и максимум.

Q3 выполняется непосредственно по каждой копии Bronze, чтобы исследовать влияние формата и сжатия на чтение исходных данных. Результаты дополнительно сверяются с эталонным запросом TPC-H.

### Результаты измерений

| Формат | Сжатие | Размер Bronze, МБ | Медиана Q3, с |
|---|---|---:|---:|
| Parquet | ZSTD | 48,698 | 1,522 |
| Parquet | GZIP | 48,923 | 1,652 |
| ORC | GZIP | 52,273 | 1,685 |
| ORC | ZSTD | 54,271 | 1,498 |

Результаты относятся к локальному окружению проекта и могут отличаться на других компьютерах.

### Анализ результатов

- Parquet с ZSTD показал наименьший размер файлов среди проверенных конфигураций.
- ORC с ZSTD показал наименьшую медиану времени выполнения Q3.
- Parquet с GZIP оказался немного больше Parquet с ZSTD и показал более высокое время выполнения запроса в проведённом тесте.
- Выбор формата зависит от приоритетов: экономии места или скорости чтения.

Таким образом, минимальный размер хранения не обязательно означает минимальное время выполнения аналитического запроса. Для корректного сравнения важно учитывать конфигурацию системы, прогрев, кеширование и характер нагрузки.

## 6. Проверка качества данных

В проекте предусмотрены проверки, результаты которых сохраняются в `results/checks.json`.

Проверяются:

- пропуски в обязательных полях;
- допустимые диапазоны цен и скидок;
- дубли ключей;
- потерянные связи между таблицами;
- совпадение результата Gold с эталонным запросом;
- корректность изменения схемы;
- восстановление данных из снимка.

Для сравнения выручки Gold с эталонным запросом используется допуск `0.00001`, поскольку исходный запрос применяет `DOUBLE`, а витрина использует `DECIMAL`.

### Schema evolution

Для демонстрации изменения схемы в таблицу добавляется колонка `source_system`, после чего она переименовывается в `data_source`.

У существующих записей новое поле первоначально имеет значение `NULL`. Это позволяет показать изменение схемы таблицы без необходимости заново создавать все данные.

### Time travel

Для демонстрации восстановления сохраняется идентификатор снимка Silver. Затем изменяются данные, после чего выполняется чтение предыдущей версии и восстановление таблицы с помощью `rollback_to_snapshot`.

Идентификатор снимка зависит от конкретного запуска. Перед повторным экспериментом необходимо проверить актуальные значения в `$snapshots`.

## 7. Дополнительная обработка с Apache Spark

Spark используется как дополнительный инструмент обработки данных Bronze.

Для подключения применяется JDBC-драйвер Trino версии 476.

Скачать драйвер и запустить сценарий можно из PowerShell:

```powershell
Invoke-WebRequest 'https://repo.maven.apache.org/maven2/io/trino/trino-jdbc/476/trino-jdbc-476.jar' -OutFile 'scripts/trino-jdbc-476.jar'

docker compose --profile tools run --rm spark
```

Выполняются следующие действия:

1. Подключение Spark к Trino через JDBC.
2. Чтение таблицы `iceberg.bronze.customer`.
3. Вывод схемы и первых пяти строк.
4. Группировка клиентов по сегментам.
5. Проверка общего количества клиентов.
6. Сохранение результата в `results/spark_bronze.json`.

В данном сценарии Trino предоставляет доступ к таблице, а Spark выполняет обработку DataFrame. Прямое подключение Spark к Iceberg REST Catalog в рамках работы не настраивается.

## 9. Выводы

В ходе практической работы был реализован локальный Lakehouse с использованием Apache Iceberg, Trino, Lakekeeper и S3-совместимого объектного хранилища. Построен ELT-конвейер с разделением данных на Bronze, Silver и Gold, реализованы проверки качества и сверка аналитической витрины с эталонным запросом TPC-H Q3. Проведено сравнение форматов Parquet и ORC с алгоритмами сжатия GZIP и ZSTD по размеру данных и времени выполнения запроса. Результаты показали, что выбор оптимальной конфигурации зависит от требований к хранению и производительности. Дополнительно продемонстрированы изменение схемы таблицы, восстановление снимка и обработка данных с помощью Apache Spark.
