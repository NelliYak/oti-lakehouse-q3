# Отчёт по практической №1 — локальный Lakehouse

## 1. Вариант и масштаб

| Поле | Значение |
|---|---|
| ФИО (как в VK Education) | Якупова Нелли Рафаэлевна |
| Вариант | 1 — Q3 Shipping Priority |
| Масштаб | sf1 |
| Почему выбран | Docker доступно около 8 ГБ памяти. sf1 даёт миллионы позиций и позволяет проверить конвейер и выполнить локальные измерения. У Trino ограничение контейнера 4 ГБ. |

## 2. Сервисы и решения

| Сервис | Роль | Обоснование |
|---|---|---|
| Silo, форк MinIO | Файлы в S3-хранилище | S3-совместимость и локальное развёртывание; актуальный официальный минимальный пример Lakekeeper использует этот форк. Старый официальный образ MinIO недоступен при настройке; замена явно раскрыта. Сервис в Compose называется minio. |
| PostgreSQL 16 | Служебные данные Lakekeeper | Транзакционная БД, поддерживаемая выбранным каталогом. Не хранит строки TPC-H. |
| Lakekeeper 0.14.0 | Iceberg REST Catalog | Открытый каталог с REST-интерфейсом, отделяет метаданные от SQL-движка. |
| Trino 476 | Генерация, ELT и SQL | Есть TPC-H и Iceberg-коннекторы; один движок для загрузки и аналитики без отдельного ETL-приложения. |
| Spark 3.5.3 | Дополнительный инструмент | Чтение Bronze через JDBC и агрегация DataFrame; взаимодействие через уже настроенный Trino. |

Команды реального развёртывания (полный состав — docker-compose.yml):

```powershell
docker compose up -d minio lakekeeper trino
python scripts/setup.py
python scripts/run.py
docker compose --profile tools run --rm spark
```

Вывод docker compose ps и версии/идентификаторы образов сохранены в results/services.txt и results/images.txt.

## 3. Разбор запроса

| Таблица | Колонки | Использование |
|---|---|---|
| customer | custkey, mktsegment | Соединение с orders, фильтр BUILDING |
| orders | orderkey, custkey, orderdate, shippriority | Соединения, дата до 1995-03-15, группировка и вывод |
| lineitem | orderkey, extendedprice, discount, shipdate; дополнительно linenumber | Соединение, отгрузка после 1995-03-15, сумма цены со скидкой; linenumber проверяет ключ позиции |

Q3 суммирует только позиции, удовлетворяющие фильтру отгрузки. Формула: extendedprice × (1 − discount). Gold — 10 заказов с максимальной суммой.

## 4. Медальон

МБ = 1 000 000 байт. Вес — текущие активные файлы данных из Iceberg $files, без метаданных, исторических файлов и delete-файлов. Таблицы слоёв — самостоятельные Iceberg-таблицы, физически записанные в бакет lakehouse.

### Bronze

Сохранены исходные значения необходимых колонок, без фильтров Q3. Базовый слой — PARQUET/ZSTD. Тестовые копии вынесены в отдельные схемы.

| orders | orderkey, custkey, orderdate, shippriority | 1,500,000 | 6.986856 | PARQUET | ZSTD | Нет | Колонный формат, ZSTD как базовый кодек; без партиций для ограничения маленьких файлов на sf1. |
| lineitem | orderkey, linenumber, extendedprice, discount, shipdate | 6,001,215 | 41.474922 | PARQUET | ZSTD | Нет | Колонный формат, ZSTD как базовый кодек; без партиций для ограничения маленьких файлов на sf1. |

### Silver

Проверены NULL, уникальность ключей, связи, неотрицательные цены и скидки 0–1. Нарушений не обнаружено: их число сохранено в checks.json. Значения сегмента нормализованы upper(trim(...)); таблицы соединены, применены даты Q3. Денежные колонки приведены к DECIMAL, рассчитана line_revenue с четырьмя знаками после запятой. Дедупликация не выполнялась, поскольку дубли не обнаружены.

### Gold

Агрегирование Silver по orderkey, orderdate, shippriority; сортировка выручки и LIMIT 10. Для просмотра сохранённой таблицы ORDER BY выполняется повторно, поскольку физическая таблица не гарантирует порядок.

| Таблица | Колонки | Строк | Вес, МБ | Формат | Сжатие | Партиционирование | Обоснование |
|---|---|---:|---:|---|---|---|---|
| shipping_priority | orderkey, revenue, orderdate, shippriority | 10 | 0.000841 | PARQUET | ZSTD | Нет | Колонный формат, ZSTD как базовый кодек; без партиций для ограничения маленьких файлов на sf1. |

Gold совпал с исходным Q3 по ключам, датам и приоритету; разница выручки менее 0.00001. Допуск учитывает DOUBLE в исходном запросе и DECIMAL в Silver/Gold. Каждая комбинация Bronze проверена на совпадение с исходным запросом.

## 5. Тесты производительности

В Trino 476 кодек записи задаётся настройкой сессии iceberg.compression_codec; в SQL-файлах сохранён SET SESSION, а Python передаёт X-Trino-Session. Для ORC настройка GZIP соответствует внутреннему кодеку ZLIB; для Parquet — GZIP. Это особенности реализации форматов, а не одинаковый контейнер сжатия.

Четыре комбинации имеют одинаковые колонки, строки и отсутствие партиционирования. Для каждой выполнены один прогрев и пять измеряемых Q3 по Bronze. Порядок комбинаций чередуется. Кеш ОС не очищается: тест прогретый. Время — клиентский wall-clock с получением всех строк; серверная статистика и query id сохранены отдельно. Запись — один замер CTAS на таблицу, сумма трёх замеров; сравнение записи ориентировочное из-за прогрева и отсутствия повторений. Размер рассчитан по активным файлам, а не объёму всего бакета.

| Формат | Кодек | Размер Bronze, МБ | Запись 3 таблиц, с | Медиана Q3, с | Мин.–макс., с |
|---|---|---:|---:|---:|---|
| PARQUET | ZSTD | 48.698 | 25.080 | 1.522 | 1.444–1.590 |
| PARQUET | GZIP | 48.923 | 14.678 | 1.652 | 1.546–1.801 |
| ORC | GZIP | 52.273 | 11.698 | 1.685 | 1.546–2.142 |
| ORC | ZSTD | 54.271 | 8.065 | 1.498 | 1.442–1.505 |

Самый компактный вариант в этом запуске: **PARQUET/ZSTD**. Наименьшая медиана Q3: **ORC/ZSTD**. Эти результаты относятся к данному компьютеру, sf1 и текущему набору колонок. На другом масштабе или при холодном кеше порядок может измениться. PARQUET/ZSTD оставлен базовым слоем для единой конфигурации конвейера; результаты бенчмарка сохраняются независимо от этого выбора.

Исходные измерения: results/benchmark.csv, benchmark.json и query_log.json. Нет оснований приравнивать коэффициент сжатия к энтропии источника: результат также зависит от структуры формата, типов, кодирования колонок и служебных накладных расходов. Сжатие без потерь сохраняет аналитический результат; баланс размера и затрат CPU измеряется экспериментально.

## 6. Осмысление и инструменты

### 6.1. Объяснение и эксперименты

| Вопрос | Ответ |
|---|---|
| Зачем Lakehouse и большие данные? | Для больших аналитических наборов удобно отделять файлы в объектном хранилище от вычислительного движка и использовать открытые форматы. Iceberg добавляет таблицам снапшоты и управление схемой. Для небольшой транзакционной задачи обычная БД может быть проще; sf1 здесь выбран для обучения архитектуре, а не как доказательство необходимости больших данных. |
| Schema evolution | В Silver добавлена source_system VARCHAR и переименована в data_source. У всех прежних строк новое поле NULL; count(data_source)=0. Число строк сохранено. SQL и реальные результаты доступны в sql/schema_evolution.sql и query_log.json. |
| Time travel и восстановление | Сохранён snapshot_id 2653687598250934620. До удаления 30519 строк, после удаления позиций одного заказа 30517. Чтение FOR VERSION AS OF вернуло 30519; после rollback_to_snapshot снова 30519. Скрипт: sql/time_travel.sql. |

### 6.2. Дополнительный инструмент

| Инструмент | Почему выбран |
|---|---|
| Apache Spark в Docker | Поддерживает DataFrame и JDBC; показывает чтение Bronze и отдельное вычисление агрегата без настройки ещё одного постоянно работающего хранилища. |

Реальные действия в консоли: скачан trino-jdbc-476.jar, запущен spark-submit через Docker Compose; JDBC URL jdbc:trino://trino:8080/iceberg/bronze; прочитана customer, выведены схема и 5 строк, выполнена группировка mktsegment с count(*). Итоговая сумма клиентов проверена assert: 150000. Результаты — spark_bronze.json и spark_console.txt. Spark использует Trino как SQL-шлюз, прямой доступ к S3/REST Catalog здесь не демонстрируется.

## 7. Выводы

Bronze сохраняет исходные данные, Silver содержит проверенные и обогащённые позиции заказов, Gold отвечает на бизнес-вопрос о топ-10 по выручке.
Разделение слоёв позволяет проверить каждую стадию и повторно получить результат.
В проведённом тесте наименьший размер получен у PARQUET/ZSTD, а наименьшая медиана запроса — у ORC/ZSTD.
Выбор формата и кодека зависит от баланса места, записи и чтения, поэтому вывод ограничен условиями измерения.
Iceberg позволил изменить схему и восстановить предыдущий снапшот с сохранением правильного числа строк.
